# Deployment

humux is designed to run as a single Docker container on any VPS. It runs comfortably on a small server.

## Resource requirements

| Component | RAM | CPU | Disk |
|-----------|-----|-----|------|
| Python agent + FastAPI | ~100 MB | Minimal | — |
| Himalaya binary | ~20 MB | Per-call | ~50 MB |
| Whisper `base` model | ~300 MB | 1 core during STT | 150 MB |
| WhatsApp (wacli) | ~60 MB | Minimal | — |
| SQLite databases | ~10 MB | Minimal | Grows |
| **Total** | **~530 MB** | **2 cores** | **~500 MB** |

**Recommendation:** 2 vCPU / 2 GB RAM VPS ($5-10/month on Hetzner, Contabo, etc.)

## Docker Compose deployment

### 1. Clone and configure

```bash
git clone https://github.com/mattmezza/humux.git
cd humux
cp .env.example .env
cp config.yml.example config.yml
cp character.md.example character.md
```

### 2. Edit configuration

Fill in `.env` with your API keys and secrets. Customize `config.yml` for your needs.

### 3. Start

```bash
docker compose up -d
```

### 4. View logs

```bash
docker compose logs -f
```

## Docker image

humux publishes Docker images to GitHub Container Registry on every release:

```bash
docker pull ghcr.io/mattmezza/humux:latest
```

### Available tags

| Tag | Description |
|-----|-------------|
| `latest` | Latest stable release |
| `0.1.0` | Specific version |
| `0.1` | Latest patch for minor version |
| `0` | Latest minor for major version |

### Coding toolchains

The image includes Node.js (`node`, `npm`, `npx`) and Go by default for coding
workspace builds. Go is copied from the `golang:1.25-bookworm` wacli builder, so
both stages always use the same Go version. The runtime also includes the C/C++
compiler and `pkg-config` for CGO projects. These commands run through the coding
harness and its permission rules.

Opt out independently when building a smaller image:

```bash
cd humux
docker build --build-arg INSTALL_NODE=false --build-arg INSTALL_GO=false -t humux:lean .
```

`GOTOOLCHAIN=local` prevents automatic toolchain downloads. Repositories requiring
a newer Go version need an image with a matching builder version. `GOPATH` is
`/app/data/go`, and `GOCACHE` is `/app/data/go-build-cache`; the existing data
volume preserves module downloads and compiled packages across container
recreation. Both paths are writable by the image's `humux` user. Mount `/app/data`
when using `docker run` directly, too.

To smoke-test a built image as its default non-root user:

```bash
docker run --rm -i --entrypoint sh humux:latest -s < tests/smoke_go_toolchain.sh
# The opt-out image should have no Go executable (wacli remains available):
docker run --rm -i --entrypoint sh humux:lean -s -- disabled < tests/smoke_go_toolchain.sh
```

The enabled smoke test compiles, tests, and vets a small CGO program using only
the standard library, so it needs no module downloads.

### Bundled embedding model

The image **prefetches the local embedding model** (semantic memory, Tier 2) at build time into `/app/models` — outside the `/app/data` volume, so the mounted volume can't shadow it. The container therefore works offline with no runtime download. The model is overridable at build via the `EMBED_MODEL` build arg (keep it in sync with `memory.embedding.model`). See [Memory → Tier 2](/docs/memory#tier-2-semantic-retrieval-relevance-ranked-injection).

## Volumes and persistence

The Docker Compose file mounts these paths:

| Host path | Container path | Purpose |
|-----------|---------------|---------|
| `./data` | `/app/data` | SQLite databases, Whisper models, sessions, Go module/build caches |
| `./config.yml` | `/app/config.yml` | Agent configuration (read-only) |
| `./character.md` | `/app/character.md` | Agent identity & personality |
| `./skills` | `/app/skills` | Skill files (read-only) |

The `data/` directory is the only stateful volume. Back it up regularly.

## Security considerations

### Network
- Telegram/WhatsApp connections are **outbound-only**
- Admin API is protected by Bearer token
- Consider putting the admin UI behind a reverse proxy with HTTPS

### Secrets
- All secrets live in `.env`, never in code or config files
- The `.env` file should be readable only by root/docker

### Authentication
- **Telegram:** user ID whitelist (immutable, spoofing-proof)
- **WhatsApp:** phone number whitelist
- **Admin API:** Bearer token
- **Email:** app-specific passwords

### Data
- SQLite databases should be on an encrypted volume
- Conversation history can be auto-pruned
- No data leaves your server except to the LLM API and configured providers

## Updating

```bash
docker compose pull
docker compose up -d
```

Or pin a specific version:

```yaml
# docker-compose.yml
services:
  agent:
    image: ghcr.io/mattmezza/humux:0.1.0
```

## Releasing

Create a release with:

```bash
make release name=v0.2
```

This creates a GitHub release with auto-generated notes. The CI pipeline builds and pushes the Docker image to GHCR.
